## 18. 删除操作改为「可撤销的延迟落盘」

**收益**：删除从「不可逆」变成「5 秒内可撤销」，误删不再需要二次确认去兜（轻量操作少一次打断）。
**风险**：中 —— 删除的**语义**从「立即落盘」变为「提示消失后落盘」，牵动 5 个页面的本地状态。

### 现状（2026-09-22）

删除类底部提示已统一走 `showDeleteSnackBar(context, message:, onUndo:)`（5 秒自动消失），
但**只有收藏移除**真正带「撤销」；其余删除在弹提示之前就已经落盘，因此只显示提示、不摆撤销按钮。

| 页面 | 删除动作 | 可恢复性 |
|---|---|---|
| 历史记录（`history_center_page`）| 清空消费历史 + 搜索足迹 | 数据可快照 |
| 离线下载（`download_manager_page`）| 删任务 + **删本地文件** | 文件不可快照 → 只能延迟 |
| 站点（`site_sheets`）| `store.remove(id)` | 可快照（重新写入会换 id）|
| 规则（`rules_page`）| `removeRule(id)` | 可快照（可能级联清理关联数据）|
| 自定义规则源（`adblock_rules_page`）| `deleteCustomSource(id)` | 可快照 |
| 日志（`logs_page`）| `AppLogger.clear()` | **无还原意义 → 保持纯提示** |

### 候选方案

1. **延迟落盘（推荐）**：点击删除后**立即从界面移除**（悲观列表 → 本地乐观态），同时弹 `showDeleteSnackBar`；
   - 用户点「撤销」→ 恢复本地态，**不落盘**；
   - 提示 `closed`（含超时 / 划走 / 被下一条顶掉）→ 才真正执行删除。
   离线下载只能走这条（文件删了无法还原）。
2. **立即删除 + 快照还原**：删除前保存对象快照，撤销时重新写入。适合「清空全部」这类批量操作，实现更简单；
   但站点 / 规则重新写入会生成**新 id**，若别处按 id 引用会失联，需逐个确认。
3. **维持现状**：仅保留二次确认，不引入撤销。日志清空归此类。

### 必须处理的边界

- **提示消失即落盘**：页面在窗口期内被销毁、或 App 被杀 → 不能在 `dispose` 里丢弃待删除项，
  应在 `closed` 回调与 `dispose` 两条路径上都确保落盘（宁可删掉，也不要「提示关了但数据还在」）。
- **连续删除多条**：`showDeleteSnackBar` 会 `hideCurrentSnackBar` 顶掉上一条 → 上一条必须**立即落盘**，
  否则那次删除会被静默丢弃。
- **窗口期内的读取**：延迟期间用户重新进入该列表 / 搜索到同一条 → 乐观态要能隐藏已标记删除的项，
  不能出现「提示说已删除、列表里又冒出来」。

### 落地顺序建议

先做**离线下载**（语义最硬：延迟是唯一可行解）→ 再做**历史 / 站点 / 规则 / 自定义规则源**
（可复用同一套「乐观列表 + 延迟落盘」骨架）。日志保持纯提示不动。
