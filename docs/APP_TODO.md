## 18. 删除操作改为「可撤销的延迟落盘」

**收益**：删除从「不可逆」变成「5 秒内可撤销」，误删不再需要二次确认去兜（轻量操作少一次打断）。
**风险**：中 —— 删除的**语义**从「立即落盘」变为「提示消失后落盘」，牵动 5 个页面的本地状态。

### 现状（2026-09-22）

删除类底部提示已统一走 `showDeleteSnackBar(context, message:, onUndo:)`（5 秒自动消失），
但**只有收藏移除**真正带「撤销」；其余删除在弹提示之前就已经落盘，因此只显示提示、不摆撤销按钮。

| 页面 | 删除动作 | 可恢复性 |
|---|---|---|
| 历史记录（`history_center_page`）| 清空消费历史 + 搜索足迹 | 数据可快照 |
| 离线下载（`download_manager_page`）| 删任务 + **删本地文件** | 文件不可快照 → 只能延迟 |
| 站点（`site_sheets`）| `store.remove(id)` | 可快照（重新写入会换 id）|
| 规则（`rules_page`）| `removeRule(id)` | 可快照（可能级联清理关联数据）|
| 自定义规则源（`adblock_rules_page`）| `deleteCustomSource(id)` | 可快照 |
| 日志（`logs_page`）| `AppLogger.clear()` | **无还原意义 → 保持纯提示** |

### 候选方案

1. **延迟落盘（推荐）**：点击删除后**立即从界面移除**（悲观列表 → 本地乐观态），同时弹 `showDeleteSnackBar`；
   - 用户点「撤销」→ 恢复本地态，**不落盘**；
   - 提示 `closed`（含超时 / 划走 / 被下一条顶掉）→ 才真正执行删除。
   离线下载只能走这条（文件删了无法还原）。
2. **立即删除 + 快照还原**：删除前保存对象快照，撤销时重新写入。适合「清空全部」这类批量操作，实现更简单；
   但站点 / 规则重新写入会生成**新 id**，若别处按 id 引用会失联，需逐个确认。
3. **维持现状**：仅保留二次确认，不引入撤销。日志清空归此类。

### 必须处理的边界

- **提示消失即落盘**：页面在窗口期内被销毁、或 App 被杀 → 不能在 `dispose` 里丢弃待删除项，
  应在 `closed` 回调与 `dispose` 两条路径上都确保落盘（宁可删掉，也不要「提示关了但数据还在」）。
- **连续删除多条**：`showDeleteSnackBar` 会 `hideCurrentSnackBar` 顶掉上一条 → 上一条必须**立即落盘**，
  否则那次删除会被静默丢弃。
- **窗口期内的读取**：延迟期间用户重新进入该列表 / 搜索到同一条 → 乐观态要能隐藏已标记删除的项，
  不能出现「提示说已删除、列表里又冒出来」。

### 落地顺序建议

先做**离线下载**（语义最硬：延迟是唯一可行解）→ 再做**历史 / 站点 / 规则 / 自定义规则源**
（可复用同一套「乐观列表 + 延迟落盘」骨架）。日志保持纯提示不动。

## 19. 规则拆出独立管理页

**收益**：首页回归「使用」语义（看不到管理噪音、也不会被误改状态）；管理动作从「长按藏匿」变成显式入口，可发现性与可维护性都提升。
**风险**：低 —— **本期不含编辑**（见下），因此没有新的写入路径：启用 / 删除 / 测试 / 查看都是把已有能力搬到显式入口，剩下要额外想清楚的只有「首页过滤后如何可解释」。

### 现状（2026-09-23）

规则 Tab 现在是**手势二分**：点击 = 进入该规则的分类发现（使用），长按 = 管理面板（调试 / 分类浏览 / 复制源站地址 / 删除）。
管理被藏在长按里不可发现；列表本身是「库存视角」，顶部还挂着「搜规则名称、类型或地址」与导入入口 —— 一页承担两种心智。

已有能力（新页面主要是**聚合入口**，不是新开发）：

| 能力 | 现状 |
|---|---|
| 启用 / 禁用 / 删除 / 增改 | `RuleService.toggleRule / deleteRule / addOrUpdateRule` |
| 导入（URL / JSON / 市场）| `importFromUrl / importFromJson` + `market_page` |
| 连通性 ping、批量体检 | `pingRule / pingAllRules / disableFailedRules / removeFailedRules` + `latenciesNotifier` |
| 四阶段调试 + 控制台 + 可复制报告 | `rule_test_pipeline` / `rule_tester_page` |
| 规则内容浏览 | `rule_catalog_page` |

**缺口**：只读的「查看规则」—— 全仓**没有**任何地方能看单条规则的元信息与 JS 代码（长按面板只有「复制源站地址」）。

**本期明确不做**：规则编辑（全仓无 `ruleEditor` / `editRule`）—— 它涉及**写入**，先要解决同步冲突与校验策略，理由见下。

### 已定决策

- **「有效」= 已启用**（`rule.enabled`），**不含连通性** —— 连通性继续用徽标表达（`_buildLatencyBadge` 已有）。
  若把「ping 通过」也算有效，源站抽风时规则会从首页凭空消失，用户会当成规则丢了。
- **入口两个，指向同一个管理页**：设置 → 「规则沙箱与网络解析」卡片下；「我的」页「我的规则」资产卡
  （当前只是 `onSwitchTab(1)` 切到规则 Tab，改一行即可）。
- **不新增第三个底部 Tab**：管理是低频场景，不值得占首页一格。

### 职责划分

| 使用侧（首页规则 Tab）| 管理侧（RuleManagementPage）|
|---|---|
| 点击规则 → 分类发现浏览 | 启用 / 禁用（含批量）|
| 切源、按源搜索内容 | 导入（URL / JSON / 市场）、导出 |
| | 排序、复制源站地址 |
| | 连通性体检：单条 ping、批量 ping、失败规则一键禁用 / 清理 |
| | 调试与测试：四阶段流水线、控制台、报告复制 |
| | 删除（保留二次确认）、**查看**（只读：元信息 + JS 代码 + 复制）|

### 「查看」代替「编辑」（本期决策）

编辑是**写入**，要先想清三件事才算安全，故本期不做 —— 放弃编辑的代价远小于做错编辑：

1. **改过的规则不能被市场同步冲掉** → 需要 `localModified` 标记；
2. **校验程度** → 最少 JSON 结构 + `name / baseUrl / type / code` 必填，有条件在沙箱预跑一遍；
3. **能编辑谁** → 市场订阅源默认只读，要改就「另存为本地规则」。

改为**只读查看**：展开单条规则的元信息（`name / baseUrl / type / author / version / enabled / createdAt / updatedAt`）
与 JS 代码（`rule.code`，等宽字体），并提供「复制代码 / 复制规则 JSON」。

成本很低（无写入、无校验、无持久化），却回答了最高频的疑问：「这条规则到底配了什么」。
若连只读查看也不加，直接从管理页去掉即可 —— 列表项只剩 启用 / 删除 / 测试。

### 落地顺序（每步可独立回退）

1. `RuleManagementPage` 骨架 + 两个入口，聚合**已有**的批量体检 / 导入导出 / 单条调试入口；
   **首页一行不改**（风险为零，先让入口存在并被真实使用）。
2. 「启用 / 删除 / 测试」搬入，首页卡上的启用开关撤掉（避免双入口改状态）。
3. 首页只显示已启用规则 + **「已隐藏 N 条未启用规则 · 去管理」提示** —— 让「消失」永远可解释。
4. 补上「查看」（只读详情 + 复制）—— 可选、成本极低；**编辑不在本期范围**。

### 首页侧需顺带清理

- 卡上的**启用开关撤掉**（管理页专管）；
- 长按面板只留使用项：**删除 / 调试**进管理页；
- 顶部「搜规则名称、类型或地址」的搜索框改为搜内容，或移走。
